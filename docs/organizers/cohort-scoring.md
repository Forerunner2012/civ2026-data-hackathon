# Score a full cohort

Use `civ.evaluation-plan/v1alpha2` to replay every selected track submission against each product assigned to that track. The plan binds the participant cutoff, replay runtime, product and manifest hashes, topic and schema contracts, organizer truth, and scoring decisions. See the [plan schema](../../schemas/civ.evaluation-plan.v1alpha2.schema.json).

The plan's `participants` list is the organizer's complete registered-team roster. Include every team, including teams that submitted no tracks. The scorer emits `missing-track` outcomes for rostered teams without an eligible delivery. Receipts for unregistered identities, receipts without a track ID, and receipts with unknown track IDs block readiness and remain visible with delivery IDs and reconciliation dispositions in `summary.json`.

`score-batch` keeps the `v1alpha1` diagnostic path for older two-dataset ledgers. For a `v1alpha2` plan, `--labels` is not used because each track and product names its own organizer truth pack.

## Record track-specific deliveries

Use one stable track ID for each submission. For a local delivery, run:

```sh
uv run civ intake-local SUBMISSION.zip --ledger INTAKE_LEDGER \
  --identity TEAM_ID --track-id TRACK_ID --received-at ISO8601_TIMESTAMP \
  --sha256 BUNDLE_SHA256 --delivery-id DELIVERY_ID
```

The `intake-form` response can include a `track_id` field. Tally CSV exports can add a `Track ID` column before `Your submission.zip`. The importer accepts both the original and track-aware header sets.

The ledger keeps every valid receipt. `score-batch` selects the latest receipt on or before the plan cutoff for each identity and track. When timestamps tie, the plan must choose either `earlier_ledger_sequence` or `later_ledger_sequence`. This sequence is the receipt order in the immutable ledger snapshot. A failed selected delivery stays failed. The scorer never substitutes an older delivery.

The receipt `status` field still reflects the historical intake cutoff. Cohort selection uses the cutoff in the `v1alpha2` plan.

## Bind the runtime actually used

The `runtime` object includes measured `implementation_sha256` and `environment_sha256` values. The implementation hash covers the imported `civ_workshop` source tree, so editable-checkout changes alter the identity even when the package version and Git revision do not. The environment hash includes the resolved Python executable path and file hash, Python implementation and version, installed distribution names and versions, and the checkout's `uv.lock` hash when present. It also hashes files from the installed transitive runtime dependency inventories. File records are sorted, and caches and generated bytecode are excluded.

The plan, preflight runtime rehearsal, and cohort input fingerprint bind both hashes. The trusted replay subprocess measures them again before running `civ detect` and stops if the implementation or environment differs from the plan.

## Bind products and replay inputs

Create one track entry for each target. Add every assigned warm-up, development, and sealed product. A product reference contains paths and SHA-256 values for the MCAP, its `civ.data-product-manifest/v1`, and its `civ.label-pack/v1alpha1` truth pack.

Set `partition` to `warmup`, `development`, or `sealed`. Set `dataset` to the source family. Use a distinct `product_id` within each track. The same product can appear on two tracks with different truth packs.

Each product's `input_contract` names its configured topics and exact schema identities. Schema records use `topic`, `schema_name`, `schema_encoding`, `schema_sha256`, and `message_encoding`. The scorer checks the plan against the product manifest and the MCAP itself.

Each track's `replay` record sets accepted EventSpec contracts, allowed signal topics, resource file and byte limits, a timeout, and a retry count. The timeout applies to each trusted replay attempt. `retries` counts attempts after the first. The scorer validates the ZIP, loads only `detector/detector.yaml` and its declared resources, then invokes `civ detect` on every assigned product. It does not run the submitted reproduction script or use submitted `events.jsonl` and `metrics.json` as predictions.

The evaluator writes one result for every identity, track, and assigned product. A successful replay with zero events has `status: "scored"` and `replay.zero_events: true`. Invalid submissions, products, or replay runs have an explicit failure result. Results and replay events belong in organizer-controlled storage.

## Declare scoring decisions

Add `scoring_policy` to the plan before assigning points. The scorer keeps the existing temporal IoU threshold of `0.5` and one-to-one best matching. It requires explicit product weights, score-bearing partitions, handling for missing tracks, failed runs, and empty truth, a rule for receipt timestamp ties, cross-product handling, rounding, and Detection points for every track.

Set the Detection allocation for the Cave track explicitly. The existing rubric assigns 15 points to Kashiwa RT and 10 to Reims turns. It does not assign Cave Detection points. The scorer does not infer that allocation.

`score-batch` calculates participant Detection points when the plan supplies those decisions. For each participant and track, it computes product F1 from the exact TP, FP, and FN counts, applies the declared product weights to the included products, and uses that unrounded weighted mean for the Detection allocation. It rounds the displayed F1 and Detection points separately with the declared rounding mode and precision; the participant total is the sum of the rounded track allocations, rounded at the same precision.

Evidence and Reproducibility are machine-scored categories worth 15 points each under issue #168. That issue does not define the eligible validated artifacts, deterministic criteria, point mappings, or outcomes for missing and invalid inputs. No approved deterministic mapping exists in the current rubric or implementation, so both components remain pending: `score-batch` reports their points and the technical total as `null`. A legacy `human_component_scores` field may still appear in an older preflight record, but the scorer ignores it; human-entered points cannot complete machine categories. Do not execute submitted reproduction scripts. Jury and bonus decisions remain separate from these machine calculations.

## Validate readiness and approvals

Close intake writers before scoring. Read-only scoring rejects a ledger with a WAL sidecar. Run the readiness check with the exact files you plan to use:

```sh
uv run civ score-readiness --ledger INTAKE_LEDGER --plan EVALUATION_PLAN.json \
  --preflight PREFLIGHT.json --review-status REVIEW_STATUS.json \
  --approval COMPUTATION_APPROVAL.json
```

The checker hashes the plan, immutable receipt database, selected bundles, EventSpecs and resources, products and manifests, truth packs, and measured runtime identity. A run freezes the receipt selection from its initial ledger snapshot and compares it with the readiness fingerprint before replay. Immediately before publishing staged results, it reruns `check_readiness` with the same plan, preflight, review-status, and computation-approval paths. This revalidates the approval chain and each referenced rehearsal and reference-review artifact. It also compares the bound identities and scoring-input fingerprint with those accepted at the start. Any changed input or revoked approval discards staged output and preserves previously committed results.

The preflight record uses `civ.cohort-preflight/v1alpha1`. It contains `plan_sha256`, `input_fingerprint`, `ledger_designation`, a hashed `runtime_rehearsal` artifact, one hashed `reference_reviews` artifact for every track and product, and `official_blockers`. The older `human_component_scores` field is accepted for input compatibility but ignored. A ledger designation names the reviewer and exact ledger hash. A runtime rehearsal artifact uses `civ.runtime-rehearsal/v1alpha1` and records the exact plan, input fingerprint, runtime identity, tool and Python versions, measured implementation and environment hashes, and a passed outcome.

Each reference review artifact uses `civ.reference-review-approval/v1alpha1`. It names the exact track, product, target, and truth hash. It records an approved decision, complete coverage, a reviewer, and a timestamp. Reuse an existing review only when its target and bound truth match the plan. A review for left turns does not approve a right-or-left target.

The review-status record uses `civ.cohort-review-status/v1alpha1`. It binds the plan, input fingerprint, and preflight hash. It records an approving reviewer and confirms the cutoff, runtime, ledger, references, and scoring policy. The computation approval uses `civ.computation-approval/v1alpha1` and binds the same plan and input fingerprint plus the exact preflight and review-status hashes.

These records must come from the responsible organizers. The tool checks their contents and hashes. It cannot create human signoff. A computation approval does not approve publication.

Run a nonofficial cohort replay with:

```sh
uv run civ score-batch --ledger INTAKE_LEDGER --plan EVALUATION_PLAN.json \
  --output ORGANIZER_RESULTS --approval COMPUTATION_APPROVAL.json
```

The command writes `results.jsonl`, `summary.json`, and organizer-only replay artifacts under `replays/`. Each replay record reports the number of attempts; failed outcomes also report a failure stage. `summary.json` reports readiness blockers and the computed Detection portion. Nonofficial runs always set `official_score` to false. `--official` stops before creating output unless every readiness gate passes.

## Keep unresolved reference work open

The historical selected label-pack set remains unchanged and contains left-turn-only Reims references. A separately audited both-direction candidate binds compatible Reims references to the four assigned R&LT products and covers the proposed right-or-left target. Recommend that candidate for a private R&LT plan entry; its validation does not authorize replacing the selected set or changing the official evaluation plan. No additional label review is needed for the candidate's product or target compatibility. An organizer must still authorize its selection into an official plan.

The organizer-only Cave generator reuses trusted `civ detect`, the supplied Cave EventSpec and point resource, and product-bound label-pack validation. It reads each assigned product's actual `/fix` latitude and longitude trajectory and writes product-bound reference packs plus detection diagnostics and a generation index. The output directory must be outside the repository and participant outputs because diagnostics and references contain private evidence. The index binds each result to the source product, product manifest, EventSpec, location resource, detection events, and generated labels. Successful zero-encounter products produce valid empty references. Missing GNSS and invalid GNSS are reported separately. Generated references are algorithmic output; human review has not been performed.

Use the generator only for the assigned Cave products:

```sh
uv run -m civ_workshop.organizer.cave_references \
  --plan PRIVATE_EVALUATION_PLAN.json --track reims-caves-optional \
  --event-spec PRIVATE_CAVE_EVENTSPEC.yaml --locations PRIVATE_CAVE_POINTS.json \
  --output PRIVATE_OUTPUT_DIRECTORY
```

The current track-aware scorer can bind distinct references for Kashiwa RT, Reims R&LT, and Cave on the same product. Prepare proposed entries with exact product and reference hashes, while keeping them separate by track. Cave's Detection allocation and eligibility of public products for scoring remain pending organizer decisions. Do not take points from Reims turns or infer either decision from generated references. Keep the roster, receipt dispositions, and explicit missing-track outcomes supplied by the cohort workflow.

Keep Cave locations, event times, truth intervals, sealed replay events, generated references, and organizer paths out of participant materials. Participant instructions may describe the `/fix` GNSS, point-distance, threshold, and event-timing method without disclosing private locations or occurrence times.
